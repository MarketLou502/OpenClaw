OpenClaw

A personal AI assistant system, built and run from a single Mac Mini at home. This walkthrough has three depth levels — pick the one that fits.

OpenClaw is a personal AI assistant that its owner runs entirely from their own home, on their own computer — not a subscription running on someone else's servers. Think of it less like a single chatbot and more like a small, quiet household staff: there's one main assistant the owner actually talks to, and that assistant quietly loops in a handful of specialist helpers behind the scenes, the same way a personal assistant might pull in a bookkeeper for money questions or a nutritionist for meal planning — without the owner ever needing to know or care who's actually doing the work.

There are three ways in, and all three lead to the same "brain":

  • Texting it — like messaging any other contact on a phone.
  • Talking to it out loud — a smart speaker in the kitchen listens for a wake phrase, "Hey Jarvis," and answers back.
  • Glancing at a screen — a small display mounted in the kitchen shows a live dashboard: today's calendar, a grocery list, daily habit tracking, task boards, and a running summary of finances. That screen is, of all things, a repurposed Amazon Echo Show — its original Amazon software was stripped out and replaced so it could instead show this custom dashboard, quietly refreshing itself through the day like a smart fridge display.

Because the core system runs from one computer at home rather than a big company's server farm, the owner's messages, health data, finance database, and calendar state stay local by default. Some narrow integrations necessarily cross the internet: cloud AI requests go through OpenRouter, bank transaction updates come from Plaid, and Plaid's signed change notifications reach one dedicated local receiver through Tailscale Funnel. Most routine requests are still handled entirely on-device.

Day to day, this system quietly does things like: log a workout when it's mentioned in conversation, add milk to a grocery list, keep a calendar organized, watch for good sports-betting opportunities and share them, and answer general questions. It also keeps its own memory — like a diary — so it remembers context from earlier conversations instead of starting fresh every time.

OpenClaw's server side runs entirely on one Mac Mini on the owner's home network — there is no cloud hosting for the core system. Everything long-running is supervised by macOS's own process manager, launchd, as user-level agents rather than root daemons; each service gets a .plist file that keeps it auto-restarting through crashes and reboots.

OpenClaw core

"OpenClaw" itself is an installed npm package that provides the Gateway — a long-running process on port 18789 that is the single entry and exit point for all conversational traffic. It routes incoming messages to agents based on a config table (bindings) mapping channel → agent; right now, all iMessage traffic maps to exactly one agent, main.

OpenClaw supports running many isolated agents, each with its own working directory, its own persistent memory, and its own model settings. This instance runs ten: main (the one the owner actually talks to — owns the conversation, delegates the rest), scheduler (calendar only, internal, no direct channel of its own), health-tracker, goals, lists, meal-planner (renamed from chef 2026-08-02, when it gained meal-planning on top of its existing grocery-list ownership), finance-agent, research, systems-qa, and sports-betting. The two "thin" specialists — goals, lists — don't actually hold separate data; they drive one shared deterministic script against one backend service, so splitting those agents didn't split the underlying data store. meal-planner still uses that shared script for its grocery list, but has its own dedicated SQLite data layer for recipes and meal plans, mirroring health-tracker's architecture instead.

Where the "thinking" happens

Three model backends are configured:

  • Ollama — a local LLM runtime on 127.0.0.1:11434, running llama3.1:8b as the system-wide default. Nearly every agent uses this by default, meaning most requests are answered entirely on-device.
  • OpenRouter — a cloud API aggregator that proxies to hosted frontier models. main and research were the original two configured to use it; scheduler joined them 2026-08-02 after its local llama3.1:8b proved unreliable for real calendar-script execution (see §3.7 — it overwrote a real script after a path typo). All three are pinned to anthropic/claude-haiku-4-5 with automatic fallback to the local model if it's unreachable. There's no direct Anthropic or OpenAI key anywhere in the config — OpenRouter is the only path to an outside model.
  • MLX — Apple's on-device ML framework, running its own local inference server for a 4-bit Llama-3.1-8B. This exists specifically for latency-sensitive voice replies, so spoken exchanges skip both Ollama and OpenRouter in favor of the fastest local option.

How the owner reaches it

iMessage is handled by imsg, a third-party command-line tool that reads the Messages app's own local database and can send, watch, and react to messages. Access is gated to one allow-listed phone number.

The kitchen speaker ("Hey Jarvis") is a Home Assistant Voice Preview Edition device. Voice requests flow through Home Assistant into a custom ha-voice-adapter service, which either resolves the request itself through a fast deterministic path or opens an isolated main agent session (using the local MLX backend for speed) and speaks the reply back.

The kitchen dashboard screen is physically a jailbroken first-generation Amazon Echo Show 8, reflashed with a custom Android build and running a small app that's just a fullscreen web view pointed at a local page — no Amazon or Alexa software involved anymore. That page is served by dashboard-api, a purpose-built Node service on port 18795. The dashboard polls for fresh data every 60 seconds, and the device force-reloads the whole page every 30 minutes to keep memory use in check — there's no live push channel yet, by design.

Not everything needs an AI model

A plugin called shared-routine-router intercepts routine, high-frequency phrasing — "add milk to the grocery list," "mark the workout habit done" — and handles it with plain pattern-matching against a direct write into the dashboard, without ever invoking a model. Anything that doesn't match a known pattern falls through to the full main agent.

Memory

Each agent keeps memory in three layers: human-readable daily logs plus a curated summary file, full session transcripts with a parallel raw tool-call trace, and a searchable index built from both, so an agent can look up its own history rather than relying solely on what fits in its current context window.

Restarting a service

None of this config is hot-reloaded — editing openclaw.json has no effect on a running Gateway process until it's restarted, and the same is true of the other services' own config. Three different restart mechanisms show up across the project, used for three different situations, not interchangeably. The Gateway is force-restarted directly at the launchd level with launchctl kickstart -k gui/501/ai.openclaw.gateway — gui/501 is the per-user GUI launchd domain (501 being this Mac's owner's UID), and the -k flag means kill the currently-running instance first, rather than the plain kickstart's no-op if it's already up. That's distinct from launchctl unload ~/Library/LaunchAgents/<label>.plist followed by launchctl load on the same file, which fully de-registers and re-registers the job — necessary, not optional, whenever the .plist file's own contents changed, such as after whisper-mlx's vocabulary generator rewrites its --initial-prompt argument; a bare kickstart restarts the process but won't pick up a changed plist. It's also distinct from the higher-level openclaw gateway restart CLI subcommand that weekly-update.sh calls automatically after a version update — and per that script's own logged history, that CLI-level restart doesn't always reliably bring the Gateway's LaunchAgent back by itself, which is exactly why the script re-checks port 18789 afterward instead of trusting the command's exit code alone. launchctl print gui/501/<label> is the standard way to verify any of these actually took — it appears throughout the project's own migration notes as how a job's running state gets confirmed rather than assumed.

3.2 OpenClaw's own file & config layout

openclaw.json is the single root config file. Its top-level keys: meta (version/audit stamp), wizard (setup history), auth (auth-profile registry), models (provider registry — openrouter, ollama, mlx-local, each with a base URL and model list), agents (a defaults block plus the ten-entry list, each with id, workspace path, model override, and a tool-deny allowlist), bindings (the channel → agent routing table), channels (currently just imessage, with its CLI path, database path, allowlist, and DM policy), gateway (port/bind/auth mode), plugins (load paths and enable flags), and skills (a large catalog of optional built-ins — 40 entries, all but imsg disabled until 2026-08-02, when github and session-logs were added; see §3.7).

Tool surface per agent

Every agent entry's tools.deny list is the actual lever for a real cost problem, not a cosmetic config field. Every model call — every single turn, on every channel — pays for the full JSON schema of every tool the calling agent is allowed to use, whether that turn touches a tool or not; a wide-open agent carries that entire schema surface as dead weight on top of its own bootstrap docs. main is the clearest illustration: for most of this system's life it ran with no tools.deny at all — the full ~30-tool schema surface (browser, canvas, image/video/music generation, the gateway tool, raw process access, and more) on every call — while every subagent it manages was already scoped down. A same-day config backup timestamped 12:12pm still shows main at zero deny entries; the live config gave it 22 that same day, landing it in the same 16–21-entry range as every other agent (browser, canvas, cron, gateway, image_generate, music_generate, video_generate, process, web_fetch, web_search, memory_get, and write among them — main delegates writes to its specialists rather than performing them directly). exec was missing from that original 22 — see the exec-fallback caveat in §3.7 for why it was added later the same day, bringing the count to 23. This is what actually fixes a "context/cache is big, calls are getting expensive" problem: trimming what's always loaded into every call, independent of which model is answering it. The nightly session-compaction cron described below helps the same underlying problem from the other side — bounding how large a session's own history can grow — so the two changes compound rather than overlap.

Memory — three distinct tiers

  1. Human-readable: daily YYYY-MM-DD.md logs plus a curated MEMORY.md per workspace.
  2. Session transcripts: per-session .jsonl conversation logs with a parallel .trajectory.jsonl raw tool-call trace, indexed by sessions.json.
  3. Search index: a per-agent SQLite database holding chunk/full-text/vector tables — a hybrid keyword-and-embedding index over tiers 1 and 2, built with an OpenRouter-hosted embeddings model, chunked at 400 tokens with 80-token overlap, weighted by a 14-day temporal-decay half-life so recent memory ranks higher in search.

Cron

Not a flat file — a SQLite table (cron_jobs + cron_run_logs) managed through the CLI rather than hand-edited. Two active jobs: a nightly session compaction for main at 04:00, and — added 2026-08-02 — systems-qa-nightly-routing-review at 05:00, deliberately scheduled after the compaction job so the two never race (see §3.6).

3.4 The dashboard-api HTTP contract

dashboard-api has no framework and no dependencies at all — it's built directly on Node's built-in http module, with one router function matching method and path by hand. Every /api/* request must carry a bearer token read from a token file on disk; the static dashboard assets are deliberately the only routes exempt from that check (see the trust-boundary caveat below), and CORS is wide open (Access-Control-Allow-Origin: *) since the token is already the real boundary. Financial reads and writes go through spawnSync calls to the sqlite3 CLI with hand-escaped SQL rather than any ORM or driver library — a deliberately minimal-dependency choice consistent with the rest of the service.

The adapter's own deterministic fast paths run before any of this: it recognizes weather questions and answers them itself with a live lookup (a plain wttr.in request, geo-resolved from the Mac's own outbound IP — correct for a fixed home device), and it recognizes first-person food reports ("I had a banana," "log two eggs") and checks them against a local staples table only — an exact name/alias match, confidence 1.0, logged immediately with no model involved (into health-ledger.sqlite's food_entries — the one fast path that already had a durable, queryable record of what was actually said). Weather answers and shared-routine-router matches had no equivalent record until 2026-08-02, when both gained a small fire-and-forget write to ~/.openclaw/logs/voice-fastpath.jsonl, appended only after the reply is already sent so it can't add latency — purely so the nightly QA job in §3.6 has something to review; see §3.7 for the token-cost lesson that job's first real run surfaced. Anything past a staple miss — an unrecognized food, or any quantity phrasing at all ("half a cup of yogurt") — now falls straight through to the Main escalation path below instead of being guessed at locally. This replaced an earlier three-tier design that lived entirely in this file (staple, then a local USDA-index search, then a second local MLX completion for a rough estimate); it broke on a real 2026-08-02 request ("I just had a half a cup of yogurt") because the USDA-index tier searched the full unstripped phrase — zero matches — instead of the bare food name ("yogurt" alone: five matches, one with a ready "1 cup" portion — nothing in this file ever parsed a quantity out of the phrase to begin with — and the local-MLX-estimate tier then also failed, timing out at its fixed 12-second budget while the shared local model server was still mid-prompt roughly 24 seconds in (confirmed in mlx-server.log: a BrokenPipeError writing a response to a connection the client had already abandoned). See §3.7 for the full incident and the two further bugs it surfaced on the escalation path itself.

When nothing local matches — including any food report past a staple miss — the adapter opens a Gateway WebSocket connection directly and speaks its JSON-RPC protocol by hand — a fresh connection per request, not a persistent one, since the Gateway's own reference client behaves the same way. After the connect.challenge → connect → hello-ok handshake, it sends an agent request for main with a lightweight prompt mode and an explicit system-prompt addendum spelling out exactly which specialist owns which request: lists, meal-planner, goals, or scheduler for dashboard/board/list/habit/calendar actions, and — added 2026-08-02, see §3.7 — health-tracker for food/drink reports and nutrition questions. A fully offline example — finance ingestion

A launchd job polls every 60 seconds. Each cycle runs an AppleScript against Mail.app asking for message IDs from any sender containing capitalone.com in the last three days, checks those IDs against a processed_emails table in finance.db, and — for anything new — runs a second, per-message AppleScript call to pull that message's full raw MIME source. That raw source is piped over stdin into parse_transaction.py, which prefers the email's text/plain part and falls back to a small hand-rolled HTML-tag stripper for HTML-only messages. Parsing itself is plain regex against known Capital One phrasing: transaction type comes from keyword matching in the body (declined / debit / deposit / refund), the dollar amount from a $X.XX pattern, the merchant from whichever of three fallback patterns applies (a "statement as" line, a "Description:" line, or the inline phrasing used in declined-purchase emails), and the account's last four digits from a "360 Checking…####" pattern. Only debit transactions are actually kept — declined, deposit, and refund emails are parsed and logged for visibility but explicitly discarded as out of scope, and every retained row is written with a needs_review flag already set to true, so nothing reaches the dashboard as a trusted number without a human glance first. Deduplication happens at two independent layers: the poller skips message IDs it's already seen, and the parser separately hashes the full raw email (SHA-256) into a source_event_id with a unique index, so even a re-fetched or re-delivered copy of the same email can't double-write. This pipeline explicitly involves no AI or LLM at all — pure scripted automation, chosen deliberately for a task that doesn't need judgment, only reliable pattern extraction.

3.6 The deterministic router, in detail

shared-routine-router is the one piece both the iMessage path and the voice path call before anything reaches an AI model — ha-voice-adapter imports its routeRoutineRequest function directly, and the Gateway's own iMessage handling goes through the same function, so a phrase like "add milk to the grocery list" is handled identically no matter which channel it arrived on. It's a small hybrid system: a Node orchestrator (index.js) that owns dispatch and side effects, and a Python subprocess (recognize.py) that owns nothing but language understanding.

For every incoming line of text, index.js spawns recognize.py as a one-shot child process and passes it the raw text as an argument. recognize.py first runs a small cleanup pass — stripping a leading "can/could/would you [please]," a leading or trailing "please," and trailing punctuation — with one deliberately specific ordering rule: "tell me" has to be peeled off only when it follows one of those lead-in phrases, never on its own, because several intents (listing habits, listing a board, listing custom lists) use a bare "tell me" as their own trigger verb and would become unreachable if it were stripped first. The cleaned text is then handed to recognize_best() from hassil — the same sentence-matching engine Home Assistant itself uses for its voice intents — loaded with an Intents object built by merging every YAML file under sentences/en/ (currently dashboard.yaml, calendar.yaml, health.yaml, and — added 2026-08-02 for balance/forecast questions — financials.yaml) into one grammar. recognize.py prints exactly one line of JSON back to stdout — {"intent": ..., "slots": {...}}, or nulls on no match or any exception — which index.js parses and switches on.

The YAML files aren't training data, they're literal grammars: each intent lists one or more sentence templates using hassil's own syntax — (a|b|c) for alternatives, [optional] segments, and {slot} placeholders resolved against a lists: block that marks each slot as either a closed set of values or a free wildcard. dashboard.yaml is a good example of the grammar evolving with real usage: {board} is a small closed set (grocery only, now that boards and custom lists share one code path), while {list} is a wildcard — and the file carries a standing comment explaining why every sentence using {list} requires a mandatory trailing anchor word ("board" or "list") rather than an optional one: without it, testing found that an unrelated sentence like "what is the capital of Australia" would match ShowList with list="the capital of Australia", because a bare wildcard with no anchor happily swallows an entire sentence. The anchor is what keeps this router from intercepting ordinary conversation it was never meant to touch.

Back in index.js, a successful match dispatches through routeRoutineRequest's switch statement to one of four existing deterministic Node scripts — dashboard-workflow.js, calendar-workflow.js, health-workflow.js, or (added 2026-08-02, for the two balance/forecast voice intents) finance-workflow.js — invoked as a child process with plain CLI arguments and expected to print one line of JSON back. The finance case is the one exception to "these scripts perform the write/read themselves": its two voice commands call GET /api/financials over HTTP rather than querying finance.db directly, deliberately reusing dashboard-api's existing balance/forecast calculation instead of a second copy of that logic living in the router's own script. Every dispatched call carries a stable idempotency key, a SHA-256 hash of the channel, account, conversation, message ID, route, and original text, so a retried or duplicated delivery of the same message can't double-execute the same write. One route, deleting a custom list, doesn't execute immediately at all: it stores the pending action in an in-memory map keyed by channel and conversation with a 30-second expiry, replies asking for confirmation, and only runs the actual delete if the very next message in that conversation matches a yes-shaped regex — a no, an unrelated message, or simple silence past 30 seconds all fall through to normal handling instead. That confirmation state is deliberately per-process and per-channel: voice and iMessage each hold their own map, so a "yes" spoken to the kitchen speaker can never confirm a delete that was actually asked about over text.

Nightly routing QA review (added 2026-08-02)

The router above is entirely static — it only ever matches what its YAML grammar already describes, and nothing in shared-routine-router itself notices when real phrasing keeps missing it. systems-qa's second designed job (its first, still its only other one, is the narrow stuck-delegate diagnostic Main hands it when a delegated call doesn't resolve in time — workspace-systems-qa/SOUL.md's "one designed job") closes that loop: a cron-triggered agent turn, once a day, that reads yesterday's actual traffic and proposes — never applies — grammar fixes for gaps it finds.

Triggered by the openclaw cron job systems-qa-nightly-routing-review (§3.2), 05:00 daily, deliberately after the 04:00 main session-compaction job so the two never race over the same session files. sessionTarget: isolated — the run has no memory of any prior night except what it deliberately wrote to disk. It runs on a per-job model override, openrouter/anthropic/claude-haiku-4-5, not systems-qa's usual local ollama/llama3.1:8b — a deliberate choice, since drafting a grammar diff and judging whether a match "should" have happened is real reasoning, not the narrow classification job one's local model handles.

Every read and write goes through two fixed wrapper scripts, workspace-systems-qa/scripts/qa-read.sh and qa-propose.sh — the actual enforcement boundary for this job, not tools.deny: systems-qa's exec/read were never technically denied (its own TOOLS.md said "no file access" in prose only), so tools.fs.workspaceOnly: true was added to its openclaw.json entry as the one real technical guardrail — it confines the generic read/write tools to workspace-systems-qa/, but not exec, which is why the wrapper-script convention (same pattern finance-agent and scheduler already use) still carries the actual weight. qa-read.sh exposes a fixed whitelist — the session index, individual session transcripts (pre-filtered server-side to a watermark, see §3.7), the voice fast-path capture log, the router's own grammar files read fresh every run, and food-log entries since a timestamp. qa-propose.sh writes only under its own memory/, proposed-diffs/, and state/, plus one narrow named exception to truncate the shared voice-capture log after it's been read. Neither script has any path that reaches services/shared-routine-router/ itself.

Every turn since the watermark gets classified as fast-path-router, fast-path-food, fast-path-weather, or escalated-to-main. Escalated turns are checked two ways: a grammar-gap candidate is phrasing close enough to an existing intent that a slot/wildcard tweak should cover it; a fast-track candidate is three or more near-verbatim phrasings that all resolved to the same downstream action but never matched anything — the resolveAndLogFood shape (a phrase reliably resolving to a known target), just not built yet for whatever this is. Grammar-gap candidates get an actual diff drafted and validated: applied to a scratch copy of the router (never the live files), paired with a new test case in the same expectIntent/expectNoMatch style already used for real regression fixes in index.test.js, and only kept if node --test index.test.js actually passes against that scratch copy. Fast-track candidates that need real resolution logic beyond matching — fuzzy matching, confidence scoring — get a written spec instead of drafted code; that's flagged as future manual work, not something this job builds.

Output is a single small digest per day (turn counts, one line per candidate with its diff file referenced by path) written to workspace-systems-qa/memory/YYYY-MM-DD.md — nothing raw ever leaves the existing session/SQLite stores it reads from, and nothing about this job auto-loads into any other agent's context. The cron job's own delivery.mode is none — it never messages Aaron directly, consistent with job one's "findings are logged, not proactively surfaced" convention — but failureAlert is configured this time (a gap the older compaction job still has), so a broken run does reach Aaron over iMessage rather than failing silently forever.

3.7 Known caveats

macOS/browser quirk, not a voice-orb bug

Granting the voice-orb page microphone access can switch a connected Bluetooth headset from its high-quality mode (A2DP) into a low-quality call mode (HFP) at the OS level, and macOS doesn't always switch it back cleanly when the browser tab stops using it — observed during initial testing 2026-08-10 as another app ("the whisper button") suddenly seeing the headset as unusable even though it showed connected. Node itself never touches audio devices; only the browser tab's getUserMedia call does. Fix is OS-level, not code: fully quit the browser, or disconnect/reconnect the Bluetooth device in System Settings, or as a last resort sudo killall coreaudiod to restart the audio subsystem.

Protocol detail, not independently re-verified

The Gateway's JSON-RPC-2.0-over-WebSocket protocol is documented in the project's own architecture notes but could not be re-confirmed from source in this pass — the Gateway ships as a compiled npm package, not inspectable source in this repository.

Stale documentation, superseded

The kiosk frontend's own README still cites an Obsidian vault as the dashboard's data source and describes the /api/* routes as "not built yet." Both are contradicted by the fully implemented, JSON/SQLite-backed service that exists today — treat the current, working architecture described above as fact, and the vault reference as historical.

Deliberate trust boundary, not an oversight

dashboard-api's static assets are served without authentication by design — only the /api/* data routes require the bearer token. Accepted for a LAN-only device, worth knowing if the network trust model ever changes.

Retired integration

Two-way Discord bot integration was fully decommissioned. The only remaining Discord surface is a one-way script that posts sports-betting picks to a channel via a raw API call and bot token — it bypasses the Gateway's channel/binding system entirely, unlike iMessage.

Full Disk Access is binary-specific — recurs on every node upgrade

The iMessage provider (imsg) needs Full Disk Access to read ~/Library/Messages/chat.db, and macOS ties that grant to the specific node binary at /opt/homebrew/opt/node@22/bin/node. A routine brew upgrade that replaces the binary silently invalidates the grant — on 2026-08-02 this caused a 4.5+ hour total iMessage outage (the Gateway's imsg child crash-looped continuously, auto-restarting every 5–160s) with zero signal to the owner, since the very channel that would report the failure was the one that was down. The real error only surfaces in the structured per-day log at /tmp/openclaw/openclaw-<date>.log (authorization denied (code: 23)) — ~/Library/Logs/openclaw/gateway.log shows only the retry loop, because the launchd plist routes the Gateway's own stderr to /dev/null. Fix is GUI-only: re-grant Full Disk Access to the current node binary in System Settings → Privacy & Security. node@22 is now pinned (brew pin node@22) so this can't recur from a routine brew upgrade without a deliberate unpin first.

Delegated-task dual reply, fixed 2026-08-02

A QA request ("add salad to groceries") produced three assistant messages instead of one: an immediate "I'll add salad…" acknowledgment, then — 42 seconds later, 2.7 seconds apart — two near-duplicate completion messages. Session-trace inspection (agents/main/sessions/*.jsonl) showed the two completions came from different sources: one was Main's own woken-up turn composing a fresh confirmation (api: openai-completions, real token cost), the other was a separate push-based announce mechanism mirroring the spawned child's own final reply directly to the owner (model: "delivery-mirror", idempotencyKey suffixed :text-direct, zero cost — not an LLM call). Both fire independently whenever a child completes; nothing suppressed Main's own reply just because the mirror had already delivered one. Confirmed as systemic, not one-off — the same split-source duplicate appeared on a workout-log delegation earlier in the same session. Fix: workspace-main/TOOLS.md's delegation-completion section now defaults Main to NO_REPLY on wake unless it has something the auto-delivered confirmation didn't cover; it also corrected a stale instruction to poll session_status that no longer matched actual push-based behavior. The delivery-mirror mechanism itself is compiled Gateway code, not configurable from this repo — if duplicates recur after this fix, that side needs attention next.

Local-model tool-arg drift on exec's host field, fixed 2026-08-02

Same incident surfaced a second bug: the lists and meal-planner (formerly chef) specialists — both on llama3.1:8b — repeatedly failed exec calls with "host: must be equal to one of the allowed values." One traced session retried the same command 8 times, never once supplying a valid value; it guessed a device name ("Aaron's Mac mini") and a raw workspace path, both invalid — "auto" is the only value that validates, confirmed against an earlier successful call in a different session that day. Main's exec fallback bypassed delegation under subagent failure — closed 2026-08-02

When a spawned specialist errored, Main's fallback — on two separate occasions the same day, in two different domains — was to run the specialist's own backing script directly via exec rather than report the failure: once reverse-engineering workspace-daily-tracker/scripts/cal-delete.js's CLI args from source after scheduler failed on a calendar deletion, once running dashboard-workflow.js add-list-item itself after lists hit the host-validation bug above. Sub-agent channel access, audited 2026-08-02 — proactive route closed, passive route is by design

Prompted by an owner question ("do sub-agents have access to text/speak to me directly?"), audited both the inbound and outbound side of every non-main agent. Inbound is clean: iMessage is bound to agentId: "main" only (openclaw.json bindings), and the Home Assistant voice adapter hardcodes agentId: "main" for every turn (services/ha-voice-adapter/server.js:463) — no sub-agent has ever had a direct channel binding. Two bugs found and fixed, both silent failures the owner never saw a message about. First: some video posts were failing with yt_dlp.utils.DownloadError-style bot-detection ("attempting impersonation, but no impersonate target is available"). Root cause: no impersonation backend was installed. Fixed by installing curl_cffi into the Homebrew yt-dlp's own bundled Python (/opt/homebrew/Cellar/yt-dlp/<ver>/libexec/, not system Python — yt-dlp ships its own interpreter) and adding --impersonate chrome to the script's yt-dlp invocation — pinned to curl_cffi==0.13.0 specifically, since yt-dlp's own _curlcffi.py hard-rejects anything outside 0.5.10 or 0.10.x-0.15.x (pip's default latest, 0.16.0, silently left every impersonate target listed as "unavailable" with no actionable error). While verifying the fix, found a second, unrelated bug the same way: yt-dlp's auto-picked "best" format for TikTok sometimes deterministically resolves to an audio-stripped CDN mirror — same video, reproducible, confirmed directly with ffprobe -show_streams showing a video-only stream with zero audio tracks — while the download format (TikTok's own watermarked default, also offered by every post) reliably has audio. Fixed by forcing -f download/bestaudio/best instead of leaving format selection to yt-dlp's default heuristic.

Second, more consequential bug: on every one of these failures, research's own reasoning about the framework's "agent-to-agent announce step" was choosing to stay silent (ANNOUNCE_SKIP) rather than report the error back to Main — confirmed directly in the session transcript, the exact same failure logged four times in a row as the owner kept re-sending the same link expecting a different result each time, with Main never receiving any reply to relay. TOOLS.md already said to report errors plainly, but that instruction alone wasn't reliably winning against the model's own uncertainty at that generic framework decision point. Also built this pass, at the owner's request after confirming the size of the gap: automatic support for TikTok photo/slideshow posts. These are a genuinely different post type — an image carousel with no video stream at all — and yt-dlp's TikTok extractor's own _VALID_URL regex (confirmed by reading tiktok.py directly) only matches /@user/video/, never /photo/; every such URL fails with a flat Unsupported URL, falling back to yt-dlp's generic extractor. Tried the cheap options first and ruled each out concretely: a plain HTTP fetch of the photo page, even with the same Chrome TLS impersonation that fixed the video bot-detection bug above, still returns a stripped shell page with no webapp.video-detail item data in its __UNIVERSAL_DATA_FOR_REHYDRATION__ blob — this anti-bot layer specifically needs real JS execution, not just a matching fingerprint; and the public oEmbed endpoint (tiktok.com/oembed) returns a flat 400 for any /photo/ URL. Settled on a real headless browser: installed Playwright + Chromium (into the same shared whisper-mlx venv used by the rest of this pipeline, ~260MB combined) and added an automatic fallback path inside tiktok_transcribe.py itself — callers never need to know in advance which post type a URL is; a caught Unsupported URL from the video path silently redirects into the photo path in the same script run.

The photo path: loads the real page with Playwright, reads the caption straight from the og:description meta tag (far more reliable than scraping visible DOM text — TikTok's photo-mode caption isn't in a stable, easily-selected element the way the video-detail struct's title is), and pulls unique carousel images out of TikTok's Swiper.js instance. Images save to workspace-research/tmp/latest-photo-post/, overwritten on every call rather than accumulating — research is instructed to read each path in the same turn it gets them, since nothing guarantees they survive past that. If the post also has a background-audio track, its URL is pulled from the page's <audio>/<video> element, downloaded, converted with ffmpeg, and transcribed through the exact same whisper-mlx Wyoming path as a video post — a photo post can carry spoken narration over music, not just silence, so this isn't skipped.

Effort estimates: tasks gained a new field, estimatedBlocks — total effort in 30-min units, a planning concept kept deliberately separate from schedule.durationMinutes (the fixed 30-min size of one calendar work session). Added through the same layers every task field goes through: lib/taskstore.js (normalizeItem/addItem/new setItemEstimate), a new PATCH /api/tasks/:board/:id/estimate route in dashboard-api/server.js mirroring the existing /schedule sub-resource pattern, a new edit-estimate/log-progress pair of commands in dashboard-workflow.js, and a new dropdown next to the kiosk's existing due-date picker (services/dashboard-api/public/index.html/app.js). Left the existing durationMinutes !== 30 calendar-block validation untouched on purpose — a multi-hour task still only ever gets one 30-min calendar event per work session; the estimate governs pacing, not calendar-block size. First pass labeled the dropdown by raw block count ("N blocks (X min)") and capped at 20 blocks/10h; Aaron caught this immediately on first look and asked for plain duration labels instead ("Half hour", "1 hour", "1.5 hours", ...) capped at 12 hours (24 blocks) — his own framing: anything bigger should be split into more than one task. Fixed the same session, both client-side (app.js) and the server-side cap (taskstore.js's MAX_ESTIMATED_BLOCKS).

Pacing: new workspace-daily-tracker/scripts/pacing.js — for any task with both a due date and an estimate, computes blocks-remaining vs. days-remaining fresh every call; a missed day needs no separate detection, since the shrinking days-remaining denominator alone raises the day's target. Status is on-track/behind/at-risk. Progress toward an estimate is logged (0.5-block increments, doesn't require the task to be marked done) into a new append-only memory/task-progress.json. Tasks without both fields get no pacing pressure at all — deliberately scoped to what the owner called "more important" work.

Retiring the old planner: task-tracker-planner.js (the 7:30 AM habit-slot cron from the 2026-08-10 merge, described above) — the owner's own framing was "version 1," "not smart," no due-date awareness — is archived to archives/task-tracker-planner-2026-08-17/ (script, its test file, and a copy of its ai.openclaw.daily-goal-scheduler.plist, which was independently confirmed not loaded at retirement time via launchctl list — nothing needed unloading). Reactive replacement: new scripts/reassess.js, with no cron of its own — deliberately: the owner asked for "fully event-reactive," but "a day passed with no progress" is inherently something only a recurring check can notice, so this piggybacks on the already-loaded ai.openclaw.daily-tracker-heartbeat job (:00/:30) instead of adding a new one, the same trick the 2026-08-10 cue-drain already used. Each run it seeds today's habit cues once (via slot-finder.js) and decides whether any task's pacing status warrants a check-in, gated via memory/reassess-state.json so the same status never re-fires every 30 minutes. A real correctness bug was caught and fixed during this build, not in production: the first version committed "notified" state before the caller had actually attempted delivery, which would have silently swallowed a check-in on any send failure. Fixed by splitting reassess() (pure decision, no write) from a separate commitReassessState() the caller invokes only after knowing which sends actually succeeded — a failed delivery now leaves that task's state untouched so the next heartbeat tick retries it correctly.

Compose/send split: when a check-in is warranted, calendar-notification-workflow.js — still deterministic, still the only thing that calls sendNativeIMessage — asks task-tracker for a short, non-conversational, compose-only turn via a new helper, workspace-main/scripts/lib/agent-turn.js (a non-delivering openclaw agent --json CLI call, mirroring native-imessage.js's existing shell-out pattern). On compose failure or timeout, a plain deterministic fallback template is sent instead of silently dropping the check-in. This is the first place in the system where a non-live-user-turn triggers an LLM call at all — a deliberate, narrow exception, discussed and confirmed with the owner before building it, to the standing "proactive messages are deterministic" rule; the rule itself is preserved (task-tracker still never sends), only the wording is sometimes model-composed now.

Replies: a genuinely new integration, not a resurrection of the retired archives/legacy-routing-2026-07-31/ inbound watcher (which must never run alongside the native Gateway iMessage channel — investigated and confirmed still true before building this). Uses OpenClaw's existing inbound_claim plugin hook — the same production mechanism shared-routine-router already runs on — via a new plugin, plugins/task-tracker-checkin-reply/ (priority 90, below shared-routine-router's 100), registered in openclaw.json's plugins.load.paths/plugins.entries. It matches an inbound iMessage against a new correlation ledger, memory/pending-checkins.json (written when a check-in sends, 24h TTL, aged-out-not-deleted), and — on a match — asks task-tracker for a compose-only reply turn before Main's normal routing ever sees the message; more than one open check-in still routes to task-tracker with all candidates rather than guessing which task Aaron means. No match falls through to Main unclaimed, same as any other message the router doesn't handle.

One conversation at a time, added same session after Aaron watched the burst-text incident above: Aaron was explicit that this needed to feel like a person, not a task-list dump — at most one open check-in conversation at a time, no starting a second task's check-in while one is still awaiting a reply, and if he goes quiet for ~2 hours, a single gentle follow-up on that SAME task rather than a new one or repeated nagging. Implemented in reassess.js: decideCheckins now caps itself to one new check-in per run and leaves any other eligible task's state untouched (not silently marked "handled") so it's still eligible once its turn comes; reassess() checks pending-checkins.json for an open thread first and either stays silent (within the quiet window), proposes a same-task follow-up (past it), or falls through to normal selection (no open thread). recordPendingCheckin now supersedes an older open entry for the same task before adding a new one, so a reply is never seen as ambiguous against two entries about the same thing. The compose prompt (checkinFacts) was also rewritten to tell the model which of three situations it's in (fresh/recheck/follow-up) and to accept "I didn't get to it" gracefully — no guilt, no re-asking, move on.
